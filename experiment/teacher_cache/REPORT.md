# Teacher 离线缓存实验报告（RTX PRO 5000 单机 8 卡，DistMuon）

## 结论

- **提速 11.6%**：每步从 4.778 秒降到 4.224 秒（350 W，第 31–130 步）。300 W 下 500 步结果一致：4.978 → 4.394 秒，快 11.7%。省下的时间等于 teacher 前向的耗时，约 0.55 秒/步。
- **IO 不是瓶颈**：缓存放在本地 NVMe 上，即使先清空 page cache、全部从磁盘读，速度也和全部在内存里一样（4.224 秒对 4.221 秒），GPU 等数据的时间小于 1 ms/步。
- **target 与在线计算逐位一致**：DINO 的两项 target 在 530 步里逐元素完全相同。深度 target 起初有约 1/3,500 的样本存在 bf16 级别的差异，原因是预计算时每个 rank 最后一个 batch 不满 32 个样本。补满 batch 重算后，这些样本也和在线计算逐位一致，见第 4 节。
- **loss 曲线一致**：只改 target 来源、其余完全相同的 A/B（verify 模式）跑 500 步，loss 和在线计算的运行平均相差 0.72%，最后 50 步平均 0.0506 对 0.0504。这和两次在线运行之间的随机波动在同一量级。
- **成本**：预计算全部 549,787 帧用 8 卡跑了 19 分钟，缓存占 806 GiB 磁盘。
- **净收益**：按 5k 步算，每次训练省约 46 分钟（6.64 → 5.87 小时）。第一次扣掉 19 分钟的预计算，净省约 27 分钟；之后数据和 teacher 不变，每次都能省 46 分钟。
- **附带收益**：teacher 不再加载，每卡显存峰值从 70.0 GiB 降到 67.9 GiB。

## 1. 方法

每个训练步开头，三个冻结的 teacher 对每个样本跑 5 次前向，生成 4 个对齐 target。teacher 只看第一个相机（头部视角），图像为 256×256。

| target | teacher | 形状 |
|---|---|---|
| 当前帧深度 | MoGe2 → MoRGBD | 256 × 1024 |
| 未来帧（+49 帧）深度 | MoGe2 → MoRGBD | 256 × 1024 |
| DINO 当前帧特征 | DINO video | 256 × 1024 |
| DINO 未来帧特征 | DINO video | 256 × 1024 |

这些 target 只取决于样本本身：teacher 冻结，图像增强关闭，未来帧的偏移固定。所以可以对整个数据集预先算一遍，训练时由 DataLoader 按样本编号读取。

- **存储**：每种 target 一个 `.npy` 内存映射文件，按数据集的样本编号索引，bf16 格式。未来帧深度不单独存，直接读第 t+49 帧那一行的当前帧深度。episode 末尾的截断规则和 LeRobot 一致。每个样本存 1.5 MB，读 2 MB。
- **开关**：`--train.teacher_cache_dir`。不加时训练完全不变。`build` 模式生成缓存，`read` 模式读缓存训练（不加载 teacher），`verify` 模式照常运行 teacher、记录和缓存的差异、用缓存的 target 训练。
- **校验**：缓存记录数据集列表和帧数、相机顺序、teacher 权重路径、未来帧偏移和图像增强开关，任何一项不一致都会拒绝读取。

用法和复现步骤见 [README.md](README.md)。

## 2. 环境

- 8 × RTX PRO 5000 72GB，PCIe，无 NVLink；2 × AMD EPYC 9575F；内存 2.2 TB。
- 缓存放在 4 块 NVMe 组成的 RAID0 上；视频数据在另一块 RAID1 系统盘上。
- 数据：RoboTwin 2.0 clean，50 个任务，2,500 个 episode，549,787 帧。
- 配置：官方 `robotwin_dist_muon.yaml`，每卡 batch 32 × 8 卡 = 256，开启激活重算。NCCL 用默认设置，跨 NUMA 走 RDMA。
- 每组运行开始前等所有 GPU 降到 40°C 以下。所有运行都没有出现降频。

## 3. 速度

| 运行 | 功耗上限 | 统计步数 | 每步耗时 | 墙钟/步 | teacher 耗时 | 等数据 | 缓存盘读取量 |
|---|---|---|---:|---:|---:|---:|---:|
| 在线 teacher | 350 W | 31–130 | 4.778 s | 4.790 s | 541 ms | 0.2 ms | — |
| 读缓存，冷（先清空 page cache） | 350 W | 31–130 | **4.224 s** | 4.230 s | 0 | 0.4 ms | 207 GB |
| 读缓存，热（缓存已在内存） | 350 W | 31–130 | **4.221 s** | 4.220 s | 0 | 0.8 ms | 0 |
| 在线 teacher（参考） | 300 W | 31–500 | 4.978 s | 4.985 s | 557 ms | — | — |
| 读缓存 | 300 W | 31–500 | **4.394 s** | 4.404 s | 0 | 0.6 ms | 313 GB |
| verify（teacher 照常运行） | 300 W | 31–500 | 4.970 s | 4.977 s | 557 ms | 0.5 ms | 0 |

- **省下的时间等于 teacher 的耗时**：350 W 省 0.554 秒，300 W 省 0.584 秒。之前担心去掉 teacher 后，root 单元的 AllGather 会暴露出来抵消一部分收益，实际没有出现。原因是在官方代码里，这次 AllGather 本来就是在主模型 forward 开始时才发起的，teacher 前向在它之前就跑完了，原本就没有起到掩护作用。这个顾虑只在额外加了 root 参数预取的版本里才成立。
- **显存**：每卡显存峰值（nvidia-smi）从 69.98 GiB 降到 67.94 GiB；PyTorch 实际分配峰值从 53.9 GiB 降到 51.2 GiB。
- **主机内存**：训练进程占用从约 158 GB 降到约 122–141 GB。另外，缓存会被读进 page cache。

## 4. 正确性

**target 逐元素对比**：verify 模式下，每一步把缓存的 target 和在线算出的 target 逐元素比较。共 530 步（30 步 + 500 步），每步 8 卡 × 32 个样本。

| target | 有差异的步数 | 最大绝对差 | 最差一步中完全相同的元素比例 |
|---|---:|---:|---:|
| DINO 当前帧 | 0 / 530 | 0 | 100% |
| DINO 未来帧 | 0 / 530 | 0 | 100% |
| 当前帧深度 | 43 / 530 | 1.27（数值范围约 ±30） | 97.8% |
| 未来帧深度 | 39 / 530 | 2.41 | 95.5% |

上表是修复前缓存的结果。有差异时，每次都只出现在 8 个 rank 中的一个，涉及该 rank 2–4.5% 的元素，相当于约 1 个样本。

**差异的原因：预计算时最后一个 batch 不满**

- 预计算时，每个 rank 按每 32 个样本一个 batch 处理自己的样本区间，最后一个 batch 只有 19 或 20 个样本。8 个 rank 合计有 **155 个样本**是在小 batch 里算出来的，占全部样本的 1/3,547。
- 深度 teacher 做了 `torch.compile`，不同 batch 大小会编译出不同的 kernel，bf16 结果会有微小差别。训练时 teacher 永远在 32 个样本的 batch 上运行，所以训练抽到这 155 个样本之一时，就会和缓存对不上。
- **出现次数和预期吻合**：每步 256 个样本，每个样本读 2 行深度（当前帧一行，未来帧对应的一行），每步共 512 次读取，每次命中这 155 行的概率是 155/549,787。按此推算，30 步预计约 4 次，实际 4 次；500 步预计约 72 次，实际 78 次。
- **逐项验证**（单卡，`check_teacher_determinism.py`）：

| 检查 | 样本数 | 在线连跑两次的差异 | 在线 vs 缓存的差异 |
|---|---:|---:|---:|
| 随机组成的 batch（32 个样本） | 1,920 | 0 | 0 |
| 155 个尾 batch 样本 + 165 个随机样本，修复前 | 320 | 0 | **155**（恰好是全部尾 batch 样本） |
| 同上，修复后 | 320 | 0 | **0** |

  在线 teacher 对同一批输入是逐位确定的，batch 由哪些样本组成也不影响结果，只有 batch 大小会影响。
- **修复**：预计算时把每个 rank 的最后一个 batch 用重复的最后一个样本补满到 32 个，只重算这 155 行（8 卡用时 7 秒）。修复后整个缓存的随机抽查结果见附录。
- **影响很小**：修复前，这些差异只影响约 1/3,500 的样本，最大差值 2.4（数值范围约 ±30）。verify 500 步的 loss 也已经和在线运行一致。修复的目的是让缓存和在线计算逐位一致，方便以后用 verify 做检查。
- **注意**：这也意味着深度 target 和训练时的 micro batch 大小有关。如果训练改用别的 micro batch 大小（比如 16），在线算出来的深度 target 本身也会有 bf16 级别的不同。要逐位一致，缓存应该用和训练相同的 micro batch 大小来生成。

**未来帧去重是正确的**：抽查 400 个样本，"样本 t 解码出的未来帧"和"样本 t+49 解码出的当前帧"像素完全相同，其中 101 个是 episode 末尾被截断的样本（`check_future_frames.py`）。

**loss 曲线**：

| 对比 | 步数 | loss 逐步平均相对差 | VLA loss | 对齐 loss（深度 / 未来深度 / 未来视频） | 最后 50 步平均 loss |
|---|---:|---:|---:|---:|---|
| 两次在线运行（350 W，随机波动参考） | 130 | 0.37% | 0.40% | 0.09% / 0.08% / 0.03% | 0.0990 / 0.0988 |
| **verify（缓存 target）vs 在线**（300 W） | 500 | **0.72%** | 0.80% | 0.34% / 0.33% / 0.14% | **0.0506 / 0.0504** |
| 读缓存 vs 在线（300 W） | 500 | 7.42% | 8.33% | 0.44% / 0.49% / 0.54% | 0.0512 / 0.0504 |

- verify 模式和在线运行唯一的区别是 target 的来源。两者的差异只比两次在线运行之间的差异略大，而且步数更多（500 对 130），本来就会累积更多差异。所以可以认为用缓存的 target 不改变训练。
- **读缓存模式的 VLA loss 从第 1 步就和在线运行不同**，但第 1 步的四个对齐 loss 完全相同，说明数据和 target 一致。原因是读缓存时不加载 teacher，而加载 teacher 会消耗随机数，所以 flow matching 的噪声序列和在线运行不同，效果相当于换了随机种子。最后 50 步平均 loss 差 1.6%，属于随机种子级别的波动。

## 5. IO 与存储

- **需求很小**：每卡每步读 32 × 2 MB = 64 MB，8 卡合计每秒约 120 MB。
- **冷启动的读放大**：130 步按需要只读约 67 GB，磁盘实际读了 207 GB，放大约 3 倍，原因是内核对内存映射文件的随机读做了预读。启动阶段瞬时读速最高约 9.4 GB/s，但 GPU 等数据的时间仍然小于 1 ms/步，因为 DataLoader 的 worker 在后台读、提前预取了下一个 batch。如果放在慢盘上，可以改用 `pread` 或 `madvise(MADV_RANDOM)` 去掉这部分放大。
- **存储量**：缓存大小约为 1.5 MB × 帧数，和相机数量无关。本数据集 55 万帧，缓存 806 GiB，约为原始视频数据（66 GB）的 12 倍。存成 fp8 可以减半，但需要另做 loss 验证。
- **对机器的要求**：
  - 必须有能放下缓存的本地 SSD。用机械盘或网络盘需要单独测试。
  - 内存够大时，缓存会自然留在 page cache 里，但这不是必需条件：本实验中冷启动和热启动的速度一样。
  - 在容器里使用时，DataLoader 的 worker 需要足够的共享内存（`--shm-size` 或 `--ipc=host`）。
- **预计算的速度**：8 卡每秒约 480 个样本，瓶颈在 CPU 视频解码（GPU 利用率不高）。数据有增加时，只需对新帧补算。目前的实现支持中断后从断点继续，还不支持追加新数据。

## 6. 限制与后续

1. **随机数序列偏移**：读缓存模式的 flow matching 噪声和同一随机种子的在线运行不同，所以两种模式的结果不能逐位对齐，统计上是等价的。如果需要逐位一致，可以在加载 teacher 的前后保存并恢复随机数状态，但这会改变默认的在线行为，需要单独评估。
2. **缓存的有效条件**：打开 `image_augment`，或者更换数据集、teacher 权重、相机顺序后，缓存都要重建。代码会检查并拒绝不匹配的缓存。
3. **可以进一步优化**：缓存模式下，DataLoader 仍然为三个相机解码了未来帧，其实已经不需要了。去掉可以减少 CPU 开销，目前数据加载不是瓶颈，所以还没做。
4. **增量追加**：数据增加时，只为新的 episode 补算缓存。
5. **缓存不解决 root AllGather**：每步 forward 开始前收集 ViT、embed_tokens 和对齐头参数的那次 AllGather（约 1.9 GB），缓存前后都一样存在。缓存去掉了 teacher 前向，root 预取也就失去了用来掩盖它的计算。后续可以考虑：ViT 逐层 FSDP；或者让 root 单元在 forward 后不重新切分参数，每卡多占约 1.9 GB 显存，正好可以用缓存省下的显存来换。

- 同一批输入在线跑两次：差异 0
- 在线 vs 缓存：差异 0

另外，用修复后的缓存跑了一次 5 步的 read 训练，确认加入相机顺序后的缓存校验能正常通过。

注意：运行多个检查进程时要限制每个进程的线程数（比如 `OMP_NUM_THREADS=12`）。否则每个进程都会按 CPU 总核数开线程，进程之间互相抢占，整机负载会升到 500 左右，检查速度慢一个数量级。
